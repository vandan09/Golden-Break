## Phase 2 notes
- **`SpriteRenderer.DOFade` (from `DOTweenModuleSprite.cs`, a Demigiant module file under `Assets/Plugins`, no asmdef) didn't resolve from `GoldenBreak.Runtime`**, even though other DOTween calls from the same assembly (`DOTween.Sequence()`, `.transform.DOScale(...)`, `.transform.DOShakePosition(...)`) compiled fine. No `DOTWEEN_NOSPRITES` symbol was defined (checked `ProjectSettings.asset` directly), no duplicate/conflicting `DOFade` definitions existed, and the file's own `.meta` was identical in structure to sibling module files that *did* resolve — so this looks like an assembly-visibility quirk specific to that one module file rather than something with an identifiable single cause. Rather than keep chasing Unity's assembly resolution internals, sidestepped it entirely: `GridManager`'s clear-flash animation now calls `DOTween.ToAlpha(...)` directly — the exact core API `DOFade` wraps internally (confirmed by reading `DOTweenModuleSprite.cs`'s own source) — instead of the extension method. Worth a look if other `DOTweenModuleSprite`/similar module-only extension methods are needed later; the core `DOTween` static methods are the reliable fallback.
- **A Phase-1-era test's premise silently broke once line-clearing was wired in, and the fix was a real design lesson, not just patching an assertion.** `EndDrag_PlacementLeavesRemainingHandUnplaceable_FiresOnGameOverBeforeAllThreeAreDone` filled the board solid except a domino-sized gap, on the assumption that placing there would leave the board "completely full." Once `LineClearDetector` runs on every placement, that assumption became false: the fill pattern happened to complete row 0 when the domino landed, which correctly triggered a clear and reopened 8 cells — so the hand *could* still fit somewhere, and `GameOverDetector` was right to say the game wasn't over. Fixed by redesigning the fill as a checkerboard (matching the sibling test already using that pattern) with exactly one even-parity cell left open for the domino gap: this structurally guarantees the placement can never complete a row or column (every row/column always keeps 3 of its 4 odd-parity cells empty), so no clear can ever fire and reopen space. General lesson for later phases: any test that pre-fills a board and asserts on post-placement state needs to account for `LineClearDetector` now running on every placement, not just `GameOverDetector`.
- **DDA weight adjustment (`DDAManager`, built in Phase 1) is not yet wired into the live `PieceSpawner` used by `GameplayController`.** `GameplayController.Awake()` still constructs `PieceSpawner` with the default `weightMultiplier: null` (flat weights). ## Phase 4 notes (foundational slice: save data/triggers, CoinManager, undo/refresh, DDA wiring)
- **Scope deliberately narrowed to the foundation everything else in Phase 4 depends on**, per BUILD_PLAN's own task grouping ("Save and load" + "Coins and economy" sections) — ads/IAP/analytics SDK integration, daily streak/challenge/milestones, push notifications, and the full UI screen set (Home/Settings/Daily Challenge/Streak popup, undo/refresh buttons) are all explicitly deferred to later slices of this same phase, not skipped.
- **`SaveManager.LoadFrom` now has a real migration hook (`Migrate`).** No migration steps exist yet (v1 is still the only schema this project has shipped) but the hook stamps `SaveVersion` up to `SaveData.CurrentSaveVersion` on load and is structured to grow a case per future version bump without touching `LoadFrom`'s own control flow. Tested (`LoadFrom_OlderSaveVersion_StampsCurrentVersionOnLoad`, `LoadFrom_AlreadyCurrentSaveVersion_LeavesDataUnchanged`).
- **`CoinManager` (new, `Assets/Scripts/Meta/CoinManager.cs`) is plain C#, not a MonoBehaviour singleton** — same reasoning as `ScoreManager`: not on BUILD_PLAN Part 1's permitted-singleton list, and has genuine per-save state a static class doesn't fit. `Earn`/`TrySpend`/`CanAfford`, balance never goes negative (`TrySpend` is a no-op-and-`false` on insufficient funds, not a clamp). 15 tests in `CoinEconomyTests.cs`.
- **`BoardState.RemovePiece` added** as the exact complement of `Place` — clears a piece's cells at a given origin. Sufficient for undo because undo is only ever legal *before* any line clear has happened since the placement (§4.5's own restriction), so there's no cascading/merge state to reconcile.
- **Undo/refresh mechanics (`PieceController.CanUndo`/`TryUndo`/`CanRefresh`/`TryRefresh`) are deliberately coin-agnostic.** `PieceController` is Core; `CoinManager` is Meta — matching the same dependency-direction rule `CeramicController`'s docstring already calls out (Core doesn't reach into Meta). Coin-cost gating (spend 50/75 coins, or grant free via a rewarded ad) is a UI-button-handler concern, explicitly deferred with the rest of the UI screen set. The mechanics themselves are fully built and tested now:
  - A `PlacementRecord?` captures the most recent placement (slot, piece, origin, colour); cleared to `null` on every new hand deal (`DealNewHand`) and on refresh, so it's never stale across a hand-cycle boundary.
  - Undo restrictions implemented exactly per §4.5: blocked once the placement cleared a line, blocked once all 3 are placed (since `DealNewHand` — called synchronously inside `EndDrag` when the hand completes — nulls the record before undo could ever be attempted), max 1 per hand (`_undoUsedThisHand`), and additionally gated on `!IsGameOver` (documented interpretation below) and `!IsDragging`.
  - Refresh restrictions per §4.5: only when all 3 unplaced (`AllPiecesUnplaced`), max 1 per hand (`_refreshUsedThisHand`). Refresh deals a fresh hand via a new private `DealHandCore` (factored out of `DealNewHand`) that does *not* reset the per-hand undo/refresh counters — only a genuine new hand-cycle (`DealNewHand`) resets them, so a player can't chain-refresh against their own refreshed hand, and undo usage from before a refresh still counts against the same hand-cycle.
  - **Deliberate interpretation, not spec'd explicitly: undo/refresh both gate on `!IsGameOver`.** Once game-over fires, the gameplay HUD (where these buttons will live) is no longer the active interaction surface — the game-over screen is. CLAUDE.md §4.5 doesn't say whether undo should be able to reverse a game-ending placement; allowing it would need `CheckGameOver`/`IsGameOver` to become resettable (currently monotonic — set once, only cleared by `RestartGame`), which is extra untested surface for a behavior nothing asked for. Flagging in case product intent differs.
  - **Deliberate scope decision: undo does not restore `ScoreManager`'s streak multiplier.** The only placement undo can ever apply to (non-clearing — a clearing placement blocks undo outright) resets the streak to ×1 via `ApplyLineClear(0)`; undoing the placement doesn't restore whatever the streak was before. Not mentioned in §4.5's undo spec; restoring it exactly would need snapshotting `ScoreManager` on every placement for a barely-visible edge case.
  - 21 tests across `UndoTests.cs` and `RefreshTests.cs`, covering every named restriction plus interaction between undo and refresh within the same hand.
- **`GameplaySaveTriggers` (new, `Assets/Scripts/Meta/GameplaySaveTriggers.cs`) closes the two save triggers from BUILD_PLAN's list that don't already have a home** (ceramic-completion and `OnApplicationPause` were already wired in `CeramicController`/`SaveManager` respectively, from Phase 3): game-over (best score, total games, total lines cleared, DDA history, game-over coin award) and any coin balance change.
  - **Depends on plain `SaveData` + a `save` delegate, not `SaveManager` itself** — `SaveManager.Current`/`Save()` only work once its own `Awake()` has run (lazily creates `_persistence` there), which EditMode tests can't reliably trigger via `AddComponent` (documented back in Phase 1; confirmed again here — `SaveManagerTests.cs` itself only ever exercises the static `LoadFrom`, never a live instance). Taking `SaveData` + `Action requestSave` instead keeps this fully unit-testable and is a strictly better design than coupling to the MonoBehaviour. `GameplayController` wires it to the real thing with `saveManager.Current` and `saveManager.Save`.
  - **This closes a real, previously-flagged gap**: Phase 2's PROGRESS notes said `SaveManager`'s `BestScore` was read once to seed `ScoreManager` but never written back. It now is (`OnGameOver` writes `score.BestScore`, which `ScoreManager` itself already keeps correctly at `max(seed, any new best this game)`).
  - **`dda_avg_score` is the *lifetime* average**, updated via the standard incremental-mean formula (`avg += (score - avg) / totalGames`) rather than a separate cumulative-sum field — CLAUDE.md §7.3's save schema only has the single `dda_avg_score` float, no running total to divide. `dda_last_10_scores` is the separate rolling-window list DDAManager already expected, capped at `Constants.DdaLast10ScoresCapacity` (10), oldest dropped first.
  - A bare line-clear (no coin change) updates `TotalLinesCleared` in memory but does *not* request a save on its own — it rides to disk at the next real trigger. This matches BUILD_PLAN's explicit 5-trigger list; total-lines-cleared isn't one of them.
  - 15 tests in `GameplaySaveTriggersTests.cs`, including a two-game sequence verifying the incremental-mean math exactly (`[10, 0]` → average `5`) and an 11-game loop verifying the last-10 window trims correctly.
- **DDA weight multiplier (flagged as an open gap in Phase 2's notes) is now wired into the live `PieceSpawner`** used by `GameplayController` — but recomputed live from `saveManager.Current` on every `PieceSpawner.SpawnOne()` call, not captured once at construction. Added a `ToastMessage` component (`Assets/Scripts/UI/ToastMessage.cs`) showing "Ad unavailable" (CLAUDE.md §5.1's required visible half of "no reward granted, player never blocked" — the no-reward half already worked, the visible-feedback half didn't) and wired `BackButtonRouter`/`HomeScreen.Show()` reuse as a pause menu so there's always a way back to Home mid-game.
  2. `HomeScreen`'s own full-screen panel (Canvas sortingOrder 25) never hid itself when opening Gallery/Settings/Daily Challenge (sortingOrder 15/20) — those screens opened *behind* Home's still-active opaque panel and silently never received a tap ("doesn't work on first click, works after clicking something else"). Fixed by centralizing the interactable refresh in one `RefreshActionButtonInteractable()` called from every relevant call site, not just `Update()`.
- **Daily Challenge went through a real design correction mid-session, not a smooth build.** The first implementation let a single shared `PieceController` snapshot/restore its state when switching between regular play and Daily Challenge (`GameModeSwitcher`, `PieceController.CaptureSnapshot`/`RestoreSnapshot`, `BoardState.SnapshotColourIds`/`RestoreColourIds`) so both were independently resumable. The user corrected the actual requirement: Daily Challenge must be a **genuinely separate, structurally distinct** game mode — not regular play resuming/pausing under a different piece sequence with a badge on it — confirmed explicitly as two requirements: (1) full technical separation, regular play must never be touched, and (2) Daily Challenge must be a genuinely *harder* challenge with different mechanics, not just a reshuffle.
  - **Fix for (1):** deleted the entire snapshot/`GameModeSwitcher` system and rebuilt Daily Challenge as a fully independent object graph — its own `GridManager`, `PieceTrayController`, and `PieceController` (see that class's own doc comment for the rationale), built once in `GameplayController.Awake()` alongside the regular one, grouped under a `DailyRoot` GameObject the regular `RegularRoot` toggles against. The two share only `CoinManager` (a global economy resource, not gameplay state) and one `InputHandler` (retargeted via a new `InputHandler.SetPieceController` — it owns no game state of its own, just "who does a raw touch currently route to"). A new `DailyChallengeSaveTriggers` (mirroring `GameplaySaveTriggers` but only ever touching `daily_completed`/`daily_best_scores`/coins) replaced the old cross-mode-aware save-trigger branch, with a test (`GameOver_DoesNotTouchRegularPlayState`) asserting regular play's `total_games`/`best_score`/streak/DDA are untouched by a Daily Challenge completion.

  - `2×3` measured as an irregular 5-cell shape; its sibling `3×2` measured as a clean solid rectangle. Corrected `2×3` to a solid 2-wide×3-tall rectangle to match.
  - `T` measured as `XXX/X..` (an L-tetromino, not T-shaped at all). Corrected to the canonical stem-in-the-middle tetromino `XXX/.X.`.
  - `L`, `S`, `Z` each measured cleanly as one of the 4 distinct "missing one corner of a 2×2" trominoes (L=missing bottom-right, S=missing top-right, Z=missing bottom-left). `J` measured identical to `L` (not distinct). User approved "corrected shapes" with a preview showing J mirrored from L (`XX/.X`) — but implementing that, I caught that it's identical to Z's already-clean shape, which would make J and Z redundant. Used the better-grounded fix instead: J = the 4th remaining distinct corner-tromino, missing top-left (`.X/XX`), completing the logical set of four without colliding with Z. Documenting this refinement since it deviates from the literal preview shown, even though "corrected, not literal" was the approved direction.
  - `J3` mirrors `L3` (vertical bar on the right instead of left, foot bottom-left instead of bottom-right), same reasoning as J/L.
  - Final 20 piece cell sets recorded directly in the `PieceDefinition` assets (`Assets/Resources/PieceDefinitions/`) — that's the source of truth going forward, not the ASCII diagram.
- **DDA "bottom/top quartile" (§3.7) has no population data to compare against** — this offline-first solo project has no backend computing global score quartiles. Approximated as the player's own last-10-game average vs. lifetime average (±25% ratio thresholds), the only distribution available on-device. See `DDAManager.cs` doc comment.
- **DDA "smaller vs larger pieces" split extended beyond spec's few named examples.** §3.7 only names 4 small examples and 3 large examples; extended to the full 20-piece set following the base weight table's own natural grouping (weight-12/10 tier = small, weight-8/6/5/3 tier = large).
- **70 EditMode tests passing, 0 compile errors** after fixing a real ambiguous-`Random`-reference bug (`UnityEngine.Random` vs `System.Random`, both in scope via `using UnityEngine`) in `PieceSpawnerTests.cs` — fixed with an explicit `using Random = System.Random;` alias.
- **Real bug caught only by actual on-device testing, not reasoning or EditMode tests: `GameplayController` built its entire grid/tray/piece hierarchy inside the wrong scene.** `[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` fires exactly once, right after the very first scene loads app-wide — it does *not* re-fire on every subsequent `SceneManager.LoadScene` call, which I had genuinely wrong. Since `GameplayController`'s bootstrap used that attribute directly, it built everything the instant the **Boot** scene loaded (the first scene), then `BootController`'s immediate `LoadScene("Gameplay")` destroyed all of it along with the rest of the Boot scene — leaving the actual Gameplay scene with its own untouched default camera (perspective, skybox), which is exactly what a device screenshot showed: a plain sky-gradient, no grid at all, despite zero crashes/exceptions in logcat. Diagnosed by adding temporary `[DIAG]`-tagged logging (now removed) and reading the exact timestamped sequence in `adb logcat`. Fixed by switching to a persistent `SceneManager.sceneLoaded` subscription (registered once via `BeforeSceneLoad`) that checks `scene.name == "Gameplay"` on every firing — correct regardless of how many times Gameplay is loaded over the app's lifetime (relevant again once "Play again" exists). `BootController`'s own use of the fire-once attribute is correct as-is, since Boot is always the first scene by construction.
- **Second real bug caught by an actual device screenshot: camera sizing only accounted for vertical extent (grid + tray), not the portrait screen's width constraint.** First screenshot after the scene-load fix showed the grid and tray *did* render correctly — piece shapes, colours, even the corrected `J` shape all visually confirmed — but both were clipped symmetrically at the left/right screen edges. Root cause: `orthographicSize` was sized purely from vertical content, and a narrow portrait aspect ratio means the resulting horizontal view (`orthographicSize * aspect`) can be narrower than the grid's actual 8-unit width. Fixed by computing `orthographicSize` as the max of the height-derived and width-derived (`gridHalfWidth / camera.aspect`) requirements, using the real runtime `camera.aspect` rather than an assumed value.
- **Phase 1 fully verified end-to-end on a real (emulated) Android device, not just build success.** Final screenshot after both fixes: full 8×8 grid rendering cleanly within screen bounds (no clipping either edge), 3-piece tray showing correctly-shaped, correctly-coloured pieces (confirmed an L-shape, a solid 3×2, and a 3×1 in that run), zero crashes/exceptions in logcat. One environment gotcha along the way worth remembering: this session's emulator frame times briefly spiked to 1000-7000ms/frame (vs. a steady ~40ms baseline) under accumulated load from a long session — a screenshot taken too early during that spike showed a near-black pre-init frame that looked like a bug but wasn't; waiting longer and re-capturing resolved it. Always check `app_time_stats` in logcat before treating an odd screenshot as a real rendering bug.
- **`InputHandler` (touch/mouse polling) is intentionally not unit-tested.** Legacy `Input.GetMouseButtonDown`/etc. can't be simulated in EditMode tests without the new Input System's `InputTestFixture` (not used here). All of the actual state-machine logic it drives lives in `PieceController` (fully tested — 15 tests covering begin/update/end-drag, valid/invalid placement, bounce-back, all-3-placed re-deal), so `InputHandler` itself is a thin, deliberately-thin adapter with nothing left to test in isolation. Same honest split as GLYPH's own "compiled but not interactively verified" input code — except here the actual game-rule logic underneath genuinely is tested, not just compiled.
- **`GameObject.AddComponent<T>()` does not reliably invoke `Awake()` synchronously in EditMode test execution** (unlike Play Mode / real gameplay, where it does). Found via `GridManagerTests`: `BuildGrid`'s 64-cell construction lived only in `Awake()`, and every test asserting on it failed with childCount=0 immediately after `AddComponent`. Fixed by extracting the construction logic to a public `BuildGrid()` method that `Awake()` calls, and having tests call it explicitly instead of relying on lifecycle timing — also just a better design (explicit, directly callable). Retroactive note: `AdManagerTests`/`AnalyticsManagerTests` (Phase 0) never actually exercised their managers' `Awake()` side effects (`Instance = this`, `DontDestroyOnLoad`) either, but the logic those tests do cover doesn't depend on Awake having run, so it's a coverage gap on trivial boilerplate, not a masked bug — not worth retrofitting given the actual gameplay logic underneath is fully covered via direct method/static calls.
- **Piece set is 20 shapes, not 18.** Spec §3.1 prose says "18 shapes" but both the ASCII diagram and the spawn-weight table enumerate 20 distinct pieces (single, 1x2, 2x1, 1x3, 3x1, 1x4, 4x1, 1x5, 5x1, 2x2, L, J, S, Z, T, 2x3, 3x2, L3, J3, 3x3). - **Two real bugs found and fixed in `Assets/Editor/ProjectSetup.cs` (original script, written for Golden Break) during Phase 0 verification, not left unverified:**
  1. `CreateFolderStructure()`'s folder list omitted `Assets/Scenes`. `EditorSceneManager.SaveScene` failed with "Parent directory must exist" — logged as an `Debug.LogError` but did not throw, so `CreateScenes()` proceeded to add three nonexistent scene paths to `EditorBuildSettings.scenes` without anything surfacing the failure. Fixed by adding the folder, and by making `CreateScenes()` verify `File.Exists` after each save and throw if it's missing, per BUILD_PLAN Part 1's "never fail silently" rule.
  2. `new EditorBuildSettingsScene(path, true)` (the string-path constructor) serializes an all-zero GUID into `EditorBuildSettings.asset` even though the scene's own `.meta` file has a correct one — confirmed across three separate rebuild attempts, including one with a post-save `AssetDatabase.Refresh()` that made no difference. Investigated further and confirmed this doesn't matter functionally: `BuildPlayerOptions.scenes` is populated directly from the `.path` field (see `BuildAndroidInternal`), never from this cached GUID, and an actual empty Android build succeeded end-to-end (`Builds/Android/GoldenBreak.apk`, 26.4MB, well under the 35MB budget) — so this is a cosmetic serialization quirk of scripted `EditorBuildSettings.scenes` assignment in batch mode on this Unity version, not a real defect. Left the GUID-typed constructor in place since it's the more correct call regardless.
