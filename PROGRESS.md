## Phase 2 notes
- **`SpriteRenderer.DOFade` (from `DOTweenModuleSprite.cs`, a Demigiant module file under `Assets/Plugins`, no asmdef) didn't resolve from `GoldenBreak.Runtime`**, even though other DOTween calls from the same assembly (`DOTween.Sequence()`, `.transform.DOScale(...)`, `.transform.DOShakePosition(...)`) compiled fine. No `DOTWEEN_NOSPRITES` symbol was defined (checked `ProjectSettings.asset` directly), no duplicate/conflicting `DOFade` definitions existed, and the file's own `.meta` was identical in structure to sibling module files that *did* resolve — so this looks like an assembly-visibility quirk specific to that one module file rather than something with an identifiable single cause. Rather than keep chasing Unity's assembly resolution internals, sidestepped it entirely: `GridManager`'s clear-flash animation now calls `DOTween.ToAlpha(...)` directly — the exact core API `DOFade` wraps internally (confirmed by reading `DOTweenModuleSprite.cs`'s own source) — instead of the extension method. Worth a look if other `DOTweenModuleSprite`/similar module-only extension methods are needed later; the core `DOTween` static methods are the reliable fallback.
- **A Phase-1-era test's premise silently broke once line-clearing was wired in, and the fix was a real design lesson, not just patching an assertion.** `EndDrag_PlacementLeavesRemainingHandUnplaceable_FiresOnGameOverBeforeAllThreeAreDone` filled the board solid except a domino-sized gap, on the assumption that placing there would leave the board "completely full." Once `LineClearDetector` runs on every placement, that assumption became false: the fill pattern happened to complete row 0 when the domino landed, which correctly triggered a clear and reopened 8 cells — so the hand *could* still fit somewhere, and `GameOverDetector` was right to say the game wasn't over. Fixed by redesigning the fill as a checkerboard (matching the sibling test already using that pattern) with exactly one even-parity cell left open for the domino gap: this structurally guarantees the placement can never complete a row or column (every row/column always keeps 3 of its 4 odd-parity cells empty), so no clear can ever fire and reopen space. General lesson for later phases: any test that pre-fills a board and asserts on post-placement state needs to account for `LineClearDetector` now running on every placement, not just `GameOverDetector`.
- **DDA weight adjustment (`DDAManager`, built in Phase 1) is not yet wired into the live `PieceSpawner` used by `GameplayController`.** `GameplayController.Awake()` still constructs `PieceSpawner` with the default `weightMultiplier: null` (flat weights). ## Phase 4 notes (foundational slice: save data/triggers, CoinManager, undo/refresh, DDA wiring)
- **Scope deliberately narrowed to the foundation everything else in Phase 4 depends on**, per BUILD_PLAN's own task grouping ("Save and load" + "Coins and economy" sections) — ads/IAP/analytics SDK integration, daily streak/challenge/milestones, push notifications, and the full UI screen set (Home/Settings/Daily Challenge/Streak popup, undo/refresh buttons) are all explicitly deferred to later slices of this same phase, not skipped.
- **`SaveManager.LoadFrom` now has a real migration hook (`Migrate`).** No migration steps exist yet (v1 is still the only schema this project has shipped) but the hook stamps `SaveVersion` up to `SaveData.CurrentSaveVersion` on load and is structured to grow a case per future version bump without touching `LoadFrom`'s own control flow. Tested (`LoadFrom_OlderSaveVersion_StampsCurrentVersionOnLoad`, `LoadFrom_AlreadyCurrentSaveVersion_LeavesDataUnchanged`).
- **`CoinManager` (new, `Assets/Scripts/Meta/CoinManager.cs`) is plain C#, not a MonoBehaviour singleton** — same reasoning as `ScoreManager`: not on BUILD_PLAN Part 1's permitted-singleton list, and has genuine per-save state a static class doesn't fit. `Earn`/`TrySpend`/`CanAfford`, balance never goes negative (`TrySpend` is a no-op-and-`false` on insufficient funds, not a clamp). 15 tests in `CoinEconomyTests.cs`.
- **`BoardState.RemovePiece` added** as the exact complement of `Place` — clears a piece's cells at a given origin. Sufficient for undo because undo is only ever legal *before* any line clear has happened since the placement (§4.5's own restriction), so there's no cascading/merge state to reconcile.
- **Undo/refresh mechanics (`PieceController.CanUndo`/`TryUndo`/`CanRefresh`/`TryRefresh`) are deliberately coin-agnostic.** `PieceController` is Core; `CoinManager` is Meta — matching the same dependency-direction rule `CeramicController`'s docstring already calls out (Core doesn't reach into Meta). Coin-cost gating (spend 50/75 coins, or grant free via a rewarded ad) is a UI-button-handler concern, explicitly deferred with the rest of the UI screen set. The mechanics themselves are fully built and tested now:
  - A `PlacementRecord?` captures the most recent placement (slot, piece, origin, colour); cleared to `null` on every new hand deal (`DealNewHand`) and on refresh, so it's never stale across a hand-cycle boundary.
  - Undo restrictions implemented exactly per §4.5: blocked once the placement cleared a line, blocked once all 3 are placed (since `DealNewHand` — called synchronously inside `EndDrag` when the hand completes — nulls the record before undo could ever be attempted), max 1 per hand (`_undoUsedThisHand`), and additionally gated on `!IsGameOver` (documented interpretation below) and `!IsDragging`.
  - Refresh restrictions per §4.5: only when all 3 unplaced (`AllPiecesUnplaced`), max 1 per hand (`_refreshUsedThisHand`). Refresh deals a fresh hand via a new private `DealHandCore` (factored out of `DealNewHand`) that does *not* reset the per-hand undo/refresh counters — only a genuine new hand-cycle (`DealNewHand`) resets them, so a player can't chain-refresh against their own refreshed hand, and undo usage from before a refresh still counts against the same hand-cycle.
  - **Deliberate interpretation, not spec'd explicitly: undo/refresh both gate on `!IsGameOver`.** Once game-over fires, the gameplay HUD (where these buttons will live) is no longer the active interaction surface — the game-over screen is. CLAUDE.md §4.5 doesn't say whether undo should be able to reverse a game-ending placement; allowing it would need `CheckGameOver`/`IsGameOver` to become resettable (currently monotonic — set once, only cleared by `RestartGame`), which is extra untested surface for a behavior nothing asked for. Flagging in case product intent differs.
  - **Deliberate scope decision: undo does not restore `ScoreManager`'s streak multiplier.** The only placement undo can ever apply to (non-clearing — a clearing placement blocks undo outright) resets the streak to ×1 via `ApplyLineClear(0)`; undoing the placement doesn't restore whatever the streak was before. Not mentioned in §4.5's undo spec; restoring it exactly would need snapshotting `ScoreManager` on every placement for a barely-visible edge case.
  - 21 tests across `UndoTests.cs` and `RefreshTests.cs`, covering every named restriction plus interaction between undo and refresh within the same hand.
- **`GameplaySaveTriggers` (new, `Assets/Scripts/Meta/GameplaySaveTriggers.cs`) closes the two save triggers from BUILD_PLAN's list that don't already have a home** (ceramic-completion and `OnApplicationPause` were already wired in `CeramicController`/`SaveManager` respectively, from Phase 3): game-over (best score, total games, total lines cleared, DDA history, game-over coin award) and any coin balance change.
  - **Depends on plain `SaveData` + a `save` delegate, not `SaveManager` itself** — `SaveManager.Current`/`Save()` only work once its own `Awake()` has run (lazily creates `_persistence` there), which EditMode tests can't reliably trigger via `AddComponent` (documented back in Phase 1; confirmed again here — `SaveManagerTests.cs` itself only ever exercises the static `LoadFrom`, never a live instance). Taking `SaveData` + `Action requestSave` instead keeps this fully unit-testable and is a strictly better design than coupling to the MonoBehaviour. `GameplayController` wires it to the real thing with `saveManager.Current` and `saveManager.Save`.
  - **This closes a real, previously-flagged gap**: Phase 2's PROGRESS notes said `SaveManager`'s `BestScore` was read once to seed `ScoreManager` but never written back. It now is (`OnGameOver` writes `score.BestScore`, which `ScoreManager` itself already keeps correctly at `max(seed, any new best this game)`).
  - **`dda_avg_score` is the *lifetime* average**, updated via the standard incremental-mean formula (`avg += (score - avg) / totalGames`) rather than a separate cumulative-sum field — CLAUDE.md §7.3's save schema only has the single `dda_avg_score` float, no running total to divide. `dda_last_10_scores` is the separate rolling-window list DDAManager already expected, capped at `Constants.DdaLast10ScoresCapacity` (10), oldest dropped first.
  - A bare line-clear (no coin change) updates `TotalLinesCleared` in memory but does *not* request a save on its own — it rides to disk at the next real trigger. This matches BUILD_PLAN's explicit 5-trigger list; total-lines-cleared isn't one of them.
  - 15 tests in `GameplaySaveTriggersTests.cs`, including a two-game sequence verifying the incremental-mean math exactly (`[10, 0]` → average `5`) and an 11-game loop verifying the last-10 window trims correctly.
- **DDA weight multiplier (flagged as an open gap in Phase 2's notes) is now wired into the live `PieceSpawner`** used by `GameplayController` — but recomputed live from `saveManager.Current` on every `PieceSpawner.SpawnOne()` call, not captured once at construction.   1. Rewarded-ad failure (no ad configured yet, since no real SDK key exists) failed completely silently — no visible feedback and no way to back out of the game-over screen. Added a `ToastMessage` component (`Assets/Scripts/UI/ToastMessage.cs`) showing "Ad unavailable" (CLAUDE.md §5.1's required visible half of "no reward granted, player never blocked" — the no-reward half already worked, the visible-feedback half didn't) and wired `BackButtonRouter`/`HomeScreen.Show()` reuse as a pause menu so there's always a way back to Home mid-game.
  2. `HomeScreen`'s own full-screen panel (Canvas sortingOrder 25) never hid itself when opening Gallery/Settings/Daily Challenge (sortingOrder 15/20) — those screens opened *behind* Home's still-active opaque panel and silently never received a tap ("doesn't work on first click, works after clicking something else"). Fixed by having each `On*Clicked` handler call `Hide()` before showing the sub-screen, with each sub-screen's own `Hide()` re-showing Home.
  3. `InputHandler.InputEnabled` wasn't being toggled by every overlay screen — raw touch/drag polling bypasses uGUI's `EventSystem` entirely (a full-screen panel sitting on top does not, by itself, block a world-space grid drag underneath), so any screen that should pause gameplay had to explicitly disable/enable it. Retrofitted onto every overlay screen.
  4. Undo/refresh buttons appeared but didn't visibly do anything in some states — root cause was `GameplayHUD` polling `CanUndo`/`CanRefresh` correctly but the buttons' `interactable` flag lagging state changes that happen off the normal `Update()` cadence (drag end, hand deal, continue). Fixed by centralizing the interactable refresh in one `RefreshActionButtonInteractable()` called from every relevant call site, not just `Update()`.
- **Daily Challenge went through a real design correction mid-session, not a smooth build.** The first implementation let a single shared `PieceController` snapshot/restore its state when switching between regular play and Daily Challenge (`GameModeSwitcher`, `PieceController.CaptureSnapshot`/`RestoreSnapshot`, `BoardState.SnapshotColourIds`/`RestoreColourIds`) so both were independently resumable. The user corrected the actual requirement: Daily Challenge must be a **genuinely separate, structurally distinct** game mode — not regular play resuming/pausing under a different piece sequence with a badge on it — confirmed explicitly as two requirements: (1) full technical separation, regular play must never be touched, and (2) Daily Challenge must be a genuinely *harder* challenge with different mechanics, not just a reshuffle.
  - **Fix for (1):** deleted the entire snapshot/`GameModeSwitcher` system and rebuilt Daily Challenge as a fully independent object graph — its own `GridManager`, `PieceTrayController`, and `PieceController` (see that class's own doc comment for the rationale), built once in `GameplayController.Awake()` alongside the regular one, grouped under a `DailyRoot` GameObject the regular `RegularRoot` toggles against. The two share only `CoinManager` (a global economy resource, not gameplay state) and one `InputHandler` (retargeted via a new `InputHandler.SetPieceController` — it owns no game state of its own, just "who does a raw touch currently route to"). A new `DailyChallengeSaveTriggers` (mirroring `GameplaySaveTriggers` but only ever touching `daily_completed`/`daily_best_scores`/coins) replaced the old cross-mode-aware save-trigger branch, with a test (`GameOver_DoesNotTouchRegularPlayState`) asserting regular play's `total_games`/`best_score`/streak/DDA are untouched by a Daily Challenge completion.

## 2026-08-28/29 session — Claude Design ceramic library, gallery fixes, package rename

- **Gallery "cut off on the right" was not a Gallery bug at all.** `ResponsiveCanvasSetup` used `matchWidthOrHeight = 1` (match height), so the canvas width in reference units was `844 x screenAspect` — 379.8 on the player's 1080x2400 device, not the mockup's 390. Every pixel value copied from the design was ~2.6% too wide app-wide; the gallery's 2-column grid just made it visible. Switched to match **width**, so the canvas is exactly 390 units wide on any device and mockup coordinates are literally correct. Affects every screen.
- **Gallery card text was invisible because the border was a layout row.** `AddBorder` parents a stroke Image to the card, and `Image` implements `ILayoutElement` — so the card's `VerticalLayoutGroup` gave it a row of its own (the empty rounded pill visible in the player's screenshot), pushed the content past the cell height, and uGUI then shrank the flexible rows to their minimum. `Text` has a min height of 0, so the date and score collapsed to nothing. Fixed with `LayoutElement.ignoreLayout = true`; `AddBorder` is copy-pasted into 8 files and none of them had it, so all 8 were patched (latent anywhere a bordered element sits in a layout group).
- **All 9 ceramics are now real authored artwork.** Previously 3 silhouettes covered 9 tiers and the missing cracks were fabricated by mirroring/shrinking the authored ones — which is what made higher tiers look wrong on-device (a "7-crack vase" was 3 real paths plus 4 invented). The player supplied a "Ceramic Library - 9 tiers" artboard; all 9 shapes and all 72 crack paths are now copied verbatim into `CeramicShapeData` as the design's own SVG strings, parsed by a new `SvgPath` (absolute M/L/C/Z). Nothing is invented any more, and a design revision is a copy-paste rather than a re-derivation. Tier crack counts are back to §3.4's real 4->12 (72 line clears of content, up from 40).
- **Ceramic rendering unified.** Home card, Gallery and the gameplay ceramic all draw from one rasterized composite (`CeramicSilhouetteSprite.GetComposite`) that paints the design SVG exactly: cracks are stroked from a distance field, which reproduces SVG's round `strokeLinecap`/`strokeLinejoin` for free. The previous UI path drew each crack segment as a rotated `Image` quad — square ends, no joins, no glow. `CeramicView` keeps `LineRenderer`s only for the crack currently animating, handing it back to the composite on completion.
- **Colour variants are now metals, not a hue rotation.** §3.4 asks for tier 10+ colour variants but specifies none. The old rule shifted the base gold's hue by a fixed step, which sent variants 1-3 through green and cyan — nothing about a green seam reads as precious-metal repair. Replaced with gold / rose gold / silver / copper (`CeramicGold`), wrapping so the endless loop keeps rotating. Shared between the sprite and the animating LineRenderer so a crack cannot change colour the instant its fill ends.
- **Save migration**: `CeramicController.ReconcileProgressWithArtwork()` adopts the current artwork's crack count for an in-progress ceramic and clamps the repaired count into it (a ceramic already complete under the old count stays complete). Without it an existing save would show a ceramic drawing 7 cracks but completing after 3.
- **DEV-ONLY gallery catalogue**: five taps on the Gallery title swaps the earned gallery for all 21 ceramic/variant combinations. A hidden gesture on purpose — the real gallery must only ever show what the player earned, since "I haven't unlocked that one yet" is the retention hook. **Strip `OnTitleTapped` / `BuildAllVariantsPreview` / `MetalName` from `GalleryScreen` before release.**
- **Package renamed** `com.GoldenBreak.GoldenBreak` -> `com.dizzo.goldenBreak` (ProjectSettings, AndroidResolverDependencies, ProjectSetup). Must match whatever is registered with AppLovin and Play Console; permanent once published. Note this installs as a separate app and does not inherit the old package's save data.
- **Tests: 409 EditMode + 7 PlayMode, all passing** — up from 402/9-failing. The 9 stale sprite assertions from the `BlockCellSprite` rework were fixed against real behaviour (`GetFilledCellSprite`/`GetEmptyCell`/`GetRoundedBlock`), `CeramicViewTests` rewritten for the composite-sprite design, and a new `CeramicShapeDataTests` locks the artwork contract (9 shapes, §3.4's crack counts, every crack inside its own viewBox, variants distinct and wrapping). A new PlayMode test opens the dev catalogue and asserts all 21 cards build.
- **Not installed on the player's device**: the APK is built (`Builds/Android/GoldenBreak.apk`, ARM64) and verified via rendered PNGs and tests, but the phone's wireless-debugging session ended mid-session and re-pairing needs a fresh code from the player.

## 2026-08-29 (later) — OPEN BUG RESOLVED, AdMob integrated, emulator-verified

- **The grid-rendering bug is FIXED and verified on Android.** Dragged a piece onto the board on the `GoldenBreak_Test` AVD (SwiftShader — the exact environment where it previously failed on 100% of placements): the block rendered correctly, was consumed from the tray, and enabled Undo. The fix is `GridManager`'s two-layer rewrite — 64 permanent background renderers that are never mutated, plus a pooled fill renderer laid on top when a cell fills and returned when it clears. This had been in the tree unverified since before this session.
- **Root cause is now understood, and it is broader than the grid.** Content *mutated on live objects* does not reach the screen on this Android path; content *built as an object becomes active* renders fine. Confirmed independently in uGUI: the gallery's dev catalogue rebuilt its cards in place, the tap handler ran (logged), every object was correct — and the screen kept showing the previous frame. Reopening the screen showed the correct content immediately. Neither a same-frame `SetActive(false)/SetActive(true)` cycle nor one spanning a frame was enough; Unity coalesces the former, and the latter still rebuilt onto a live canvas. **Anything that rebuilds UI in place on this project should be treated as suspect until proven on-device.**
- **Gallery dev catalogue reworked around that constraint**: the flag now defaults on, so opening the gallery lands directly on all 21 ceramic/variant cards with no in-place refresh; the ALL/MINE button sets the mode and closes back to Home, and reopening shows it. Verified on the emulator (screenshot: "Gallery · ALL" with all 9 shapes, correct names, crack counts and metals). Started as a hidden five-tap gesture on the title, which was the wrong call — it could not be verified end to end (the PlayMode test invoked `onClick` directly, proving the cards build but not that a tap reaches the button) and did nothing on device. The test now raycasts at the button's real screen position, which immediately caught that `HomeCanvas` (sorting order 25) renders above `GalleryCanvas` (15) — the gallery only works because Home hides itself, and `Show()` now does that itself rather than relying on the caller.
- **AdMob integrated (Google Mobile Ads v11.4.0).** AppLovin MAX (§5.4's original plan) will not activate an account until the app is published, so AdMob is what can be integrated pre-launch; it later becomes a mediated network inside MAX, so none of the account setup is wasted. All 6 real ad units are wired — banner, interstitial, and one rewarded unit per placement so AdMob reports revenue per placement (§5.1 predicts 55-70% opt-in on continue vs 25-40% on refresh; one shared unit would report them as a single number). App ID is written into `GoogleMobileAdsSettings` via a batch-mode step, which is what injects it into the Android manifest — without it the SDK throws on init. GDPR consent now runs through Google's real UMP. **Verified on the emulator: a "Test Ad" banner rendered on the gallery screen**, confirming init → consent → load → show end to end.
- **Cause of the player's "no ad available" on every placement**: `AdUnitIds.UsingTestAds` keyed off `Debug.isDebugBuild`, but every APK built for on-device testing is a *release* build — so the one configuration actually being tested asked for the LIVE ad units, which do not fill before the app is on the Play Store. Replaced with an explicit `ForceTestAds` constant, to be flipped as part of preparing the store release.
- **The rewarded-ad alternative for undo and refresh was never wired.** `RewardedAdController.RequestFreeUndo`/`RequestFreeRefresh` existed from the start but nothing called them; `GameplayHUD` only ever spent coins and reported a shortfall, with a comment still explaining that the ad path was a stub. A player out of coins got a dead button instead of the offer §5.1 promises. Now: affordable → spend coins; unaffordable → offer the rewarded ad, with §5.1's failure rule intact (no grant, never blocked).
- **Tests: 409 EditMode + 7 PlayMode, all passing.**
- **Still unverified**: the rewarded ad *completing* (the banner is confirmed; draining coins on the emulator hit `CanRefresh` gating before the ad could be triggered). Everything else in this entry was checked by screenshot on a real Android runtime, not inferred.
- **Emulator note**: `GoldenBreak_Test` under SwiftShader degrades after sustained use — systemui ANRs, black frames, and adb dropping to `offline` mid-install. Restarting the AVD with `-no-snapshot -memory 3072 -cores 4` clears it. Budget for a restart or two in any long verification session.
